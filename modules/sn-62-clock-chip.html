What this is. Two-run consolidated QA report for the Clock In/Out Chip — the worker-facing punch surface that lives in the App Shell topbar of every page and serves as the single source of truth for employee clock writes. Binding contract: TT_ClockChip_TestCases.md (92 TCs / 40 P0 / 30 P1 / 22 P2). Run 1 (2026-06-04) was admin-only; Run 2 (2026-06-05) re-attempted Employee/Manager-role TCs. Headline: chip is shipped and the core state machine works (open panel, active counter, done terminal, retry-window, token compliance). 5 real defects found — 1 P1 Hard Lock (zero i18n), 1 P2 (postMessage dismiss not handled), 3 P3 polish. All 3 regression candidates remain blocked on a credential/role provisioning gap.
Surprise #1 — Jira state drift. The chip is deployed and functional in QA (element button[data-spec-ref="[CC-6.1]"] renders on first login), but SN-63 (FE) and SN-64 (BE) sit at Backlog in Jira. Implementation is ahead of ticket status; either transitions were missed or someone pre-shipped without flipping state. Worth verifying with PM before relying on Jira lifecycle for handoff signoff.
Surprise #2 — role provisioning gap (dominant blocker). E2E_TEST_EMPLOYEE_USERNAME (gelosprout3) and E2E_TEST_MANAGER_USERNAME (gelosprout2) authenticate fine but both hold admin role. Clock In returns HTTP 403 — attendance.own.clock is not granted to admin. This single gap blocks 28+ TCs and all 3 regression candidates. Fix: grant attendance.own.clock to the existing accounts, or reprovision two new accounts with proper employee / manager roles. Memorialized as qa-employee-manager-cred-mismatch.
